# 存档迁移、遗忘语义与恢复

## 本批改变什么

原 `EmotionalMemoryStore` 公开接口保留，内部把三份分开写入的 JSON 改为 SQLite 的单一事务文档。使用 Python 标准库，不要求安装数据库服务。角色包、养成状态、关系存档、插件清单和默认美术资源没有格式改造。

本地用户的路径仍以原角色命名空间为基础：

```text
<user_data>/characters/<character_id>/memory_v2/
    emotional_memories.json       # 旧版输入，迁移后不再读取
    bond_profile.json             # 旧版输入，原文件不改写
    memory_chapters.json          # 旧版输入，原文件不改写
    memory_state.sqlite3          # schema 2 的唯一活动真源
    memory_state.initialized      # 仅包含初始化标志，无记忆正文
```

非默认 owner 使用 `characters/<character_id>/owners/<sha256(owner_id)>/memory_v2`；同时检查文档内角色与 owner，不能仅靠目录名过滤。当前桌面没有多账号 UI。

旧版 service API 也允许非默认 owner，却把它们写在共享角色目录。本次首次迁移会在 owner 专用旧文件不存在时，从共享旧文件中只选择该 owner/character 的事实及画像。章节要求完整来源属于同一 owner；无证据或丢失来源依赖的旧文本不进入模型。初始化后不会再从共享目录补读数据。

## 首次打开

1. 在创建 SQLite 文件前严格解析旧 JSON；不能把损坏 JSON 默默当空记忆。
2. 检查支持的 schema、角色和 owner，迁移有效条目并保留旧文件。
3. 将旧 deleted 条目转为持久退役 ID/来源；已有遗忘状态会建立上下文屏障。
4. 把事实、画像、章节、来源退役、epoch 和迁移标记置于同一文档，以 `BEGIN IMMEDIATE` / `synchronous=FULL` 提交。
5. 初始化 receipt 先于首次提交持久化。极端崩溃窗口选择拒绝自动恢复，而不是猜测性回读旧事实。

现有 `long_term_memory` 的允许类别经过一次迁移，运行日志等操作性内容不进入长期画像；`legacy_key` 与退役来源检查阻止重复导入。模型上下文只消费新的活动视图。

旧画像的字符串没有来源时，原值仍在导入存档，但不会直接进 prompt。旧章节需来源与内容指纹可验证。界面里的“看得到历史”不等于“模型仍可使用它”。

## 遗忘保证与保留内容

第一阶段的“忘记”保证：相关事实退出活动召回；其章节/画像依赖失效；旧 epoch 对话、缓存和晚到结果不能继续作为模型上下文；重启及旧迁移路径不能自动复活来源。

第一阶段仍可能保留：历史聊天档案、旧 JSON 备份、SQLite 逻辑删除正文/页面、来源 ID、已有音频缓存、操作系统备份、用户自行导出的文件、已经发送给外部模型或语音服务的数据。它们不应作为新 prompt 的平行事实入口，但不是全副本抹除功能。本批没有删除用户数据，也没有在测试时打开真实用户存档。

后续“永久删除”应是单独、范围清楚的产品动作，覆盖关联档案、音频、备份策略与远端能力，并考虑数据库空闲页清理。不能用静默删除用户备份来掩饰当前语义。

## 损坏或丢失时

出现以下情况会抛出 `MemoryStorageError`，停止记忆加载：未来 schema、不可解析 JSON、非有限数值、SQLite 损坏、已初始化后缺少表/行、数据库文件丢失但 receipt 仍在。预先存在的空数据库也不会被当成可安全回源的首次迁移。

这避免“为了能启动而恢复旧事实”。本批尚未增加图形化恢复向导；应保留错误与数据供人工确认。请勿把删除 `memory_state.sqlite3` 或 receipt 当作修复操作，尤其不能在执行过纠正/遗忘后自动改回旧 JSON。

receipt 不能保护“数据库与 receipt 同时丢失”或“整个目录被过时备份覆盖”：程序此时没有可信的已初始化证据。真实断电和 Windows 多进程压力也尚未验证，不能把合成故障测试表述为所有灾难恢复情形均已解决。

恢复建议：关闭应用，复制整个用户目录到另一个位置，在副本上检查受影响角色目录与 SQLite 完整性。只从明确可信、包含当前退役记录的完整备份恢复。如果只能恢复旧备份，应让用户知道备份时间及可能丢失的纠正/遗忘，不能无提示自动恢复。

## 回退代码与回退数据不同

旧 JSON 留存的目的是保留原始材料和审计，不是保证旧程序能看到升级后新写入的数据。直接运行旧程序会忽略 SQLite 中的新事实与退役标记，并可能再次读到曾经忘记的旧事实。

因此本批**没有宣称支持无损原地降级**。验收时使用副本存档；若必须回退程序，先冻结新版本数据，由用户选择恢复到升级前备份还是导出经当前有效性过滤的内容。未来的兼容导出工具必须保留纠正/遗忘语义，不能简单复制三份过期 JSON。

## 验证证据

`test_memory_lifecycle.py`、`test_memory_adversarial.py` 覆盖旧文件不改写、重复迁移、退役来源、重启、容量裁剪、异常回滚、过期、owner/角色隔离、首次坏 JSON 修复重试、已初始化数据库丢行/表/文件后拒绝回源。最终执行结果见 [verification.md](verification.md)。这些测试不替代真实 Windows 用户的备份与升级演练。
