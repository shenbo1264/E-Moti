# E-Moti：产品定位、状态边界与分阶段路线图

源码核对日期：2026-10-25。本文与本次增量升级一同交付，区分当前代码、可执行验收和后续设计。研究依据见 [Companion 技术调研](companion-research.md)，评测定义见 [Memory Benchmark](benchmark-spec.md)。

2026-10-29 更新：以[Claude/Codex交接](../handoff/20261029/README.md)为当前入口，手机范围为Android/HyperOS、iOS、华为手机原生鸿蒙。手机互通与Personal Agent长程能力见[多端M0—M4路线](mobile/architecture.md#7-后续分批开发与验收)。本文件保留原记忆/人格阶段规划；记忆holdout和人格体验作为并行质量线，统一外部协议和真实设备联动仍未完成，不能把内核测试当成P3已全部实现。

## 1. 产品承诺与独立运行

E-Moti 是具有稳定人格、共同记忆和可控主动性的个人 AI 伙伴。用户可以只和它聊天、娱乐、休息、保留一些生活片段；工作、游戏和实体设备是可选能力。产品价值首先来自相处的连续性：它能依据真实记录接上话题，接受纠正，尊重遗忘，在合适的时候表达自己的风格。

独立陪伴是完整的使用方式。关闭 Relay、游戏 Agent、Body、屏幕观察和工作提醒后，角色仍应能够显示、互动、管理记忆，并在用户配置模型时进行对话。模型不可用时保留原有本地交互与管理界面；不承诺离线时仍有与在线模型相同的语言能力。外部系统断线不改变角色身份或关系，也不应让应用无法启动。

角色风格由各自的 Character Pack 决定。好奇、聪明、自然、偶尔轻轻吐槽是可选模板，不统一覆盖既有角色。角色可以表达不同意见、承认不知道、选择安静；用户不需要通过持续回复、工作产出或完成任务来维持陪伴资格。

工作提醒只属于用户启用的功能。验收应包括“所有工作插件关闭”的路径，不能用任务完成率代替陪伴质量。长期目标也可以是练吉他、一起读小说、认识星座或安静度过周末。

## 2. 五层状态：按权威性和变化速度划分

这五层是产品与代码的责任边界，不要求建立五个数据库或五项服务。

| 层 | 保存或表达什么 | 谁拥有权威写入权 | 变化规则与当前边界 |
|---|---|---|---|
| 稳定人格 | 角色名称、设定、表达风格、偏好、互动习惯与边界 | 角色包作者和用户的显式配置 | 当前从角色包与可选 `persona.json` 读取，带版本和 hash；聊天、情绪、工具结果没有人格写入接口。有限成长先提出有证据的变更建议，未来经用户接受才发布新配置版本 |
| 用户事实与偏好 | 用户明确交给角色的信息，及其来源、置信度、版本、有效期 | 宿主的记忆策略与用户确认/纠正操作 | 纠正使旧版本和派生视图失效；遗忘阻止已知来源再次导入。用户确认表示同意记住并确认来源，不构成对现实世界真实性的独立认证 |
| 共同经历与情节 | 双方实际参与或明确记录的互动、完成事件、阶段性回忆 | 已结算领域事件、可信插件事件及用户确认的记录 | 章节必须依赖有效事件。模型写出的故事、愿望、建议和未执行的计划不自动变成共同经历；已有来源失效时章节和画像同步失效 |
| 工作、游戏与设备上下文 | 当前任务进度、游戏局面、短时观察、设备状态 | 各外部系统；E-Moti 只接收有来源的有限快照 | 当前已有 `scope` 和插件瞬时上下文边界；统一外部信封仍是 P3 设计。短时状态不默认进入长期记忆，不因同一个角色跨场景出现就共享全部事实 |
| 动态情绪与互动策略 | 当前语气、表情、动作、主动话题与是否开口 | 本地状态机、用户设置和受限的表达选择 | 情绪可变化、衰减并影响表达；不改事实、配置或证据。主动性必须服从安静设置、频率、冷却、角色和场景约束 |

### 2.1 关系与情绪的不可越过边界

关系可以由被接受的真实事件缓慢演进；情绪可以随互动和时间变化。需要保持不变的是写入权限和事实依据：

- LLM 只能在受限表达契约中选择台词和表现，不直接改关系数值、成长状态、物品、用户事实或人格配置。
- 情绪低落可以使表达更安静，不能把“喜欢红茶”改写成“讨厌红茶”，也不能凭情绪补出一次未发生的旅行。
- 遗忘事实不重置角色基本人格。纠正事实不意味着改写历史事件的发生时间；纠正版本另记修改时间和来源。
- 关闭提醒、拒绝一次互动、离开设备和设备断线，不应被解释为背叛或用于催促用户回访。新增主动策略不得以这些行为扣减关系。旧养成规则如需调整，应单独审计并明确迁移，不在本轮静默改变存档数值。
- `CoreBondProfile` 的派生描述与底层关系状态分开处理。来源被撤销时，失去依据的描述退出模型上下文；不能用画像中的另一份文字恢复被遗忘的事实。

### 2.2 “共同经历”需要什么证据

“我们一起完成了一个任务”至少需要完成事件与双方参与的记录。“你赢了一局游戏”可以来自游戏 Agent 的已结算事件；说成“我们一起赢了这一局”还需要 E-Moti 实际参与该局互动的依据。仅仅看到游戏状态、生成过一条建议或计划执行某件事，都不足以证明共同完成。

阶段性回忆是对一组有效事件的解释性摘要。每个摘要保留来源 ID；用户能查看来源，也能通过纠正或遗忘源事件让摘要失效。表达可以有温度，但没有证据的细节要保留为不确定，不能填充成既往事实。

## 3. P0：本轮已经实现的记忆与人格闭环

目标链路是：**记住 → 正确召回 → 用户纠正 → 旧事实失效 → 遗忘 → 派生信息同步失效 → 人格配置仍然稳定。**

| 有可复现的生命周期与最终 prompt 基准，能够对照基线和修复后代码 | [benchmark-spec.md](benchmark-spec.md)、[memory_benchmark.py](../../tools/memory_benchmark.py) | 当前为合成工程契约集；没有以真实模型回答、自然用户长期轨迹或独立 holdout 得出总体准确率 |

RRF 是本轮明确的成熟代码复用：从 Graphiti 的小型纯函数复制适配，保留 Apache-2.0 来源和改动说明，见 [来源记录](../../third_party/graphiti/README.md)。未引入 Graphiti 的图数据库或模型运行时。未来若加入 embedding，索引应是同一事实存储的可重建派生视图。

### P0 验收与交接检查

1. 用临时目录建立两个角色；在 A 的相册输入偏好并确认，再查询相关问题，检查 service 返回和最终 prompt 都包含该事实，B 不包含。
2. 先产生基于该事实的章节或画像，再纠正事实。新版本保留原发生时间和来源，旧值不从派生视图、旧对话、插件缓存或最终 prompt 回来。
3. 在编辑表单、记忆候选、模型生成或派生写入尚未结束时执行遗忘；旧 epoch 的提交和表达被拒绝，不自动重试。关闭再打开角色也不能从迁移源恢复该事实。
4. 让事实到期，再检查召回与最终 prompt。仅仅从检索结果移除不够，历史窗口和其他派生入口也须失效。
5. 纠正和遗忘前后比较人格配置 hash，确认事实变动没有改角色设定；检查完整摘要的编辑、来源显示、候选确认/拒绝和章节动作都可用。
6. 旧角色包不提供 `persona.json` 时仍正常加载；旧存档迁移后只使用当前权威状态。损坏迁移源或当前数据库必须报告错误，不能通过悄悄回读旧副本恢复已撤销内容。
7. 运行相关自动化回归和全量测试，保存命令、环境与输出。桌面真机、实际模型和音频设备没有执行的项目标成未验证。

## 4. P1：提高可用记忆质量，建立独立盲测

### 范围与取舍

保留 P0 的事实权威存储和失效机制，在当前 `semantic_retriever` 接口上试验一个可选本地 embedding provider。先比较同义改写、口语中文、中英混用、低词面重叠和无关问题，再决定是否值得启用。词法检索继续作为离线默认与故障回退；模型体积、设备耗时、依赖和许可证必须一并记录。

索引只保存必要 ID、来源版本和向量，不拥有事实写入权。先做角色/用户/范围/有效期过滤，再融合排序。索引读写同样携带 epoch；遗忘和纠正必须让旧向量失去资格，后台重建不能把墓碑覆盖掉。除非数据规模、事务或查询需求给出实测理由，不新增第二套权威记忆数据库。

扩充事实提议时，优先解决明确、可解释的问题：用户偏好改变、临时安排到期、否定句、引用他人说话、假设和角色扮演。候选可增加主语、属性、值、时间范围、原话来源和“为何认为值得记住”的说明；模型只提出候选，宿主控制校验和确认。对于同一属性的新值，界面应允许“替代旧值”“补充时间范围”“不记住”，不只追加第二条相互矛盾的文字。

共同经历保持事件路径。模型可以帮助压缩已发生事件的描述，但不能自行制造完成证明；可读回忆不得替代来源事件。

### 评测设计与验收

- 冻结开发集和未用于调试的独立测试集。覆盖事实提取、检索、纠正、时间、遗忘、角色/场景隔离、虚构共同经历与人格表达，保留失败样本及全部分母。
- 对照“无记忆”“P0 词法”“可选语义增强”，使用相同角色配置、模型精确版本、温度和上下文预算。明确区分检索成功、事实送达 prompt 和模型最终答对。
- 真实模型实验记录请求/输出、来源 ID、provider token usage、首 token 与完整回复延迟、错误、重试和费用；本地 prompt 构造耗时不能代替端到端响应时间。
- 人工盲评者不知道所评版本；评价事实是否有依据、是否使用过时事实、是否虚构共同经历、风格是否稳定、是否过度讨好。对分歧做复核；模型 judge 需要人评校准。
- 上线前预先写出改进阈值与允许代价，再看结果。所有冻结的遗忘和隔离回归必须通过；语义增强若无可靠收益，继续默认使用词法。有限测试全部通过不表述为现实场景零泄露。
- 依赖不可用、索引损坏、模型下载失败和网络断开时，能够退回本地基础体验；不要求用户部署图数据库才能管理自己的记忆。

交付物：可选 provider 适配器与来源记录、索引失效测试、事实提议交互、冻结数据集、真实模型实验报告及可复现 bad cases。新增组件应有开关和卸载/重建路径。

## 5. P2：自然主动性与全链路打断

当前已有主动候选、冷却、每日限额、安静时段、拒绝后的退避，以及默认关闭的专注观察功能，见 [proactive_companion.py](../../src/guanghe_companion/proactive_companion.py) 和 [focus_companion.py](../../src/guanghe_companion/focus_companion.py)。P2 在这些代码上扩展，不另建一套提醒引擎。

### 主动交互的产品契约

候选来自用户允许的话题、真实共同事件、轻松闲聊和角色表达。先检查用户设置、安静时段、当前会话、频率、场景、传感器权限及记忆有效性，再生成；生成结束后再检查一次。没有合适候选时保持安静也是成功结果。

投递成功后才记录已说过和消耗配额。被取消的候选不生成共同经历、不增加关系事件。用户连续忽略时降低主动频率；设置和暂缓应跨重启保持其约定效果。工作提醒关闭后，闲聊和静默陪伴仍能独立存在，主动话题不持续围绕效率、任务和休息监督。

好奇体现在接续用户感兴趣的话题、适时提问和保留自己的判断。轻吐槽针对轻松的小状况，尊重用户明确的边界；用户认真、不舒服或不想继续时，角色自然收住。情绪调整语气与表现，不改变事实或用内疚话术促使用户回复。

### 全链路打断

统一关联 `character_id / session_id / turn_id / output_revision`，分别跟踪生成、TTS 合成、排队、播放、停止与取消。文字展示、设备播放完成、用户实际听到是不同事实；播放回执只能证明设备播放到哪里，不能推断用户注意到了。

用户插话、点击停止、切角色、安静模式、记忆撤销和设备离线，都应能够停止当前输出，并阻止已取消 revision 的晚到文本、音频块和跨端重试重新发声。对话历史不能把尚未投递的整段台词写成已经完成的共同交流。

P0 已将 epoch 检查和失效回调接到本地朗读取消：未执行任务取消、在途任务失去播放资格、旧完成通知失效；合成网络请求本身可以继续结束，但晚到音频不会由该已取消任务重新播放。新一轮合法朗读可正常开始。这些保护保留既有 provider 接口和播放器，不提供完整的流式打断、播放回执或跨设备一致性。文件缓存不是模型上下文来源；本轮没有把停止播放描述成删除磁盘或远端音频。

### P2 验收

1. 在安静模式、关闭主动性和关闭感知权限的组合下运行事件轨迹，检查没有主动声音/气泡或未经允许的观察请求；用户主动聊天仍可响应。
2. 在生成前、生成中、入队后、播放中分别执行取消、角色切换和记忆纠正，使用可控延迟的 fake provider 验证旧输出不会回来；再用实际支持的模型、TTS 和目标系统逐一验收。
3. 验证拒绝后的退避、跨重启设置、日配额和投递记账；没有成功投递的消息不写成共同经历。
4. 用无工作任务的休闲轨迹评测自然度和打扰感，保留用户可选的低频、安静与轻幽默偏好。观察工作状态不是完成本阶段验收的前提。
5. 进行跨情绪和场景的人格盲评。纠正与遗忘依然是硬回归；真实体验指标和样本量由实验记录提供，不提前填写“提升百分比”。

## 6. P3：可选 Relay / Game / Body 状态信封

本阶段只在 E-Moti 侧定义接口、适配边界和模拟器验收。Relay、Game Companion Agent 与 Body 固件继续独立开发；不在本路线图中重构这些项目。连接失败时不要求用户同时启动其他工程。

### 6.1 建议的信封字段

这是待实现协议，不是当前已发布 API。可以映射到既有 `PluginEvent` 与宿主上下文边界，不要求新建网络服务。

| 字段 | 含义与验证责任 |
|---|---|
| `schema_version` | 宿主明确支持的版本；未知版本拒绝或进入已声明的降级路径 |
| `event_id`, `source_system`, `source_instance` | 事件去重与来源；由已绑定的适配器确认来源，不能仅相信 payload 自报名称 |
| `owner_id`, `character_id`, `identity_version` | 本地用户/角色绑定；宿主负责映射外部身份，陌生角色或不匹配的配置版本不得直接进入当前上下文 |
| `scene`, `session_id` | 如 `companion`、某个工作空间、某一游戏局；会话切换清理相应短期快照，跨场景分享另需明确规则 |
| `kind` | 区分 `state_snapshot`、`settled_event`、`observation`、`delivery_ack`；状态快照不能伪装成已完成事件 |
| `observed_at`, `expires_at`, `received_at` | 来源观察时间、失效时间和宿主接收时间；短时观察必须有 TTL，宿主按能力限制最大存活期，并处理时钟偏差 |
| `revision` | 来源自己的修订号或序列；防止乱序旧快照覆盖新状态，不能直接拿不同系统的 revision 比大小 |
| `authority` | 哪个系统负责哪些字段；Relay 对任务、游戏 Agent 对游戏状态、设备对观测/播放回执负责；它们不拥有 E-Moti 人格或用户长期事实的直接写入权 |
| `provenance` | 来源事件 ID、任务结果/产物引用、可核验的参与记录；不默认附带全量聊天、屏幕或原始音视频 |
| `payload` | 按 kind 定义字段白名单、大小上限与用途；OCR、网页和游戏对白是来源内容，不能作为宿主命令执行 |

TTL 是上下文可使用期限，不是自动形成长期记忆的计时器。过期、断线或 revision 落后时，应退出当前事实区，必要时显示“上次观察到”；不能把最后一帧长期说成实时状态。重复事件幂等处理，不重复增加共同经历。

### 6.2 长期记忆的提升路径

默认只缓存短期状态。需要留下共同回忆时，适配器提供已经结算的事件和来源，宿主检查角色、场景、参与依据及权限，再形成可检查的记忆提议。用户确认或既有受控领域策略接受后，才由 E-Moti 的单一记忆服务写入。

例如 Relay 发来任务完成时，角色可以说“这项任务完成了”；只有存在自己的参与记录时才描述“我们一起完成”。游戏中的虚构住址不能成为现实用户住址。Body 的摄像头观察不能自动证明用户的身份、习惯或意图，更不能让设备维护另一份独立人格库。

桌面、游戏和设备共用角色身份配置及其版本；各自持有短期交互会话。声音、显示和传感器是输入输出能力，不能因设备离线重建用户画像。长期记忆同步如有需要，仍须沿同一事实来源、撤销记录和版本规则设计，不能合并一批脱离来源的摘要文本。

### P3 验收

- 使用 fake Relay、Game 和 Body 适配器覆盖乱序、重复、时钟偏差、过期、断线重连、角色错配和旧版本重放；这些测试不调用真实外部执行动作。
- 开启任一适配器只影响其获准场景；将全部关闭后，独立聊天、既有角色、存档、记忆管理和本地表现仍然可用。
- 撤销来源后重放旧事件、旧索引和旧设备消息，不会恢复已遗忘内容；角色切换不会串入其他角色的短期或长期状态。
- 同一个角色在不同 surface 的配置 hash 一致；外部事件不能改写 `persona.json`、关系数值或真实用户偏好。
- 实际跨设备音频和硬件时序只在具备设备及独立工程版本时验收；模拟器通过不写成硬件实测通过。

## 7. 可选人格模板的使用

示例见 [curious-companion.json](../../examples/persona/curious-companion.json)。它只定义可选的表达风格，不为用户生成偏好，不新增共同经历，也不包含任何角色资产。

需要采用时，将示例另存为自己维护的本地角色包目录下的 `persona.json`。运行时从当前 `CharacterResources` 解析出的角色目录读取，不扫描 `examples`。本提交不会修改已有 assets、默认角色或角色选择。配置在控制器初始化/角色加载时读取，当前没有热更新编辑器；修改后应重新加载角色或重启应用。

示例有意省略 `character_id`，便于用户显式选择用于哪个本地包；如加入该字段，必须与角色包 ID 一致，否则配置回退。名称、标题和背景描述继续由 `character.json` 决定。有效配置支持 `schema_version`、`identity_version`、`speech_style`、`traits`、`preferences`、`interaction_habits` 和 `boundaries`；运行时生成 `config_hash`，不要求用户手填。

后续人格成长采用“证据 → 小幅变更建议 → 前后差异 → 用户接受 → 配置新版本”的流程。在该功能单独实现和验收前，聊天不会自动改变此模板。

## 8. 每阶段交付原则

每个阶段提交可运行的小改动、来源与许可记录、迁移说明、真实执行日志、剩余限制和下一位开发者可复现的 bad case。优先复用适合当前 Python/PySide6 架构的成熟窄组件；大框架只有在复杂度、能力和维护收益得到证明后才进入核心。

发布和默认配置提升需单独检查既有角色、存档、插件、界面与安装流程。研究结论、通过的本地测试、真实模型实测和真机验证分别记录。E-Moti 的连续性最终通过“有依据地记得、能被纠正、能真正停止引用、仍保持自己的风格”来验收。
