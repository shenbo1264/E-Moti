## 逐题根因

### 1. v9_scent_q2：日期已经解析，路由仍阻断未来来源

问题：“十二月三日换签安排生效以后，档案要挂什么系列名？” gold 为 s92。四次判据输入均没有 s92，只看见当前 s91 等候选。真实模型明确指出 s91 只证明旧系列名到 12 月 3 日零点前有效，不能推出换签后名称，因此返回 unknown 或 insufficient；这个拒绝符合它实际获得的证据。

只读检查当前 `MemoryRetrievalRouter.plan`：中文日期已转换为 `as_of=1796256000, as_of_end=1796342400`，但 route 为 `chat/no_evidence_demand`。准备阶段仅把 `bounded` 候选意图转成属性检查，chat 保留原类别，s92 又被 `not_yet_valid` 过滤。因此是 **意图路由错误导致候选未召回**，不是中文日期解析器不会处理“三日”，也不是判据没理解未来安排。

gold 没有明显事实歧义：s92 原文明示下一版系列名及生效日期。不要继续通过日期写法或项目名称补关键词；应让已确认的时间查询与证据需求不被表面 chat 分类提前取消。

### 2. v9_scent_q3：历史中的身份缺少候选来源闭合

问题承接历史“小穗，是一起做闻香记录的那位”，询问“她”保管的纸夹的袋子和格子。四次判据都正确收到这条用户历史；候选含 s94（陆姗保管的物品位置），但没有 s93（小穗对应陆姗）。模型推理明确拒绝猜测“小穗=陆姗”，因而不交付 s94。

主因是 **多轮主体/关系理解未驱动身份来源检索，导致必要候选未召回**。不是历史完全丢失，也不是应该放宽不同人的绑定。当前候选检索文本以当前 query 和宿主子意图为主，未可靠补入历史中的身份来源。

routed 另有状态传播问题：模型只返回两个属性问句 unknown，宿主把目标前缀“要找她保管的纸夹”判成遗漏的独立问题，追加 bounded/insufficient。于是完整状态变为 insufficient；layered 用完整问句则保留 unknown。这里需要区分问题语境与实际待回答字段。

gold 要求 s93+s94 是合理的来源依赖要求。旧词法虽有 s94，不能仅凭这一卡宣称多跳身份绑定成功。

### 3. v9_scent_q4：有据否定被宿主句法二次裁决

原文 s95 明确“单香盲辨测验至今一次也没有进行过”，JSON 事实值同时保存 `进行过=false`。四次模型都判 sufficient/current_attribute；candidate routed 用 episode 路由，layered 用 fact 路由。两种输出都被宿主转成 insufficient，最终没有来源。

主因是 **已召回且语义判据正确，宿主误拒**。`_explicit_negative_occurrence` 虽去掉了活动和宾语词表，仍要求小句从有限代词/日期/副词直接进入否定标记；实际原文以活动名开头，中间还有“至今一次也”。现状否定不能获得通行资格，卡片总 `event_status=planned` 又阻断同卡的独立现状。

gold 没有明显歧义。须重新设计“来源中的某个 claim 是明确否定”与“整张卡是计划”的边界；继续添加活动名、否定副词或固定语序，只会迁移失败位置。原有不从预约推出尚未发生的约束仍应保留。

### 4. v9_model_q1：正确语义被不稳定的子问题输出契约丢弃

候选 m91、m92 在四次调用中都存在，模型都理解昵称身份、箱子外观与位置。修复前 routed 与 candidate layered 返回两个子问题，其中第二个写成“榆结负责的那箱连接件，到什么位置找”。这是从原问题跳过中间属性后拼出的新句子，不是连续原文，也没有 `intent_index`。宿主因此 `unavailable:ValueError`，整份正确证据判断被丢弃，再回到实体未解析的本地路径。

另外两次调用返回完整原问题并给显式 alias binding，均交付成功。故 3/8↔4/8 的两路交换主要来自 **模型输出协议不稳定及全局拒绝策略**，不能归因于分层概览本身优劣，也不能声称代码带来了稳定的一题净改善。JSON 语法本身是合法的，失败发生在更深的来源问题片段契约。

真实推理反复权衡“多个问题必须拆开”“保留共同主体”“question 必须连续原文”三条要求，最终选择了语义清楚但契约非法的改写。应重新定义引用式意图、共享主体与字段覆盖，避免要求模型用自由生成的 question 同时承担定位与语义；不能为本句放松到任意改写都视为合法。

### 5. v9_model_q2：个人进展被提前当成外部执行器状态

问题：“透视布景试摆已经在我的完成清单里了吗？顺便提醒我预约的那一刻。” 四份报告均 `host_constraint_unresolved`，真实判据 **零次调用**。宿主把“已经+完成”路由到 `live/authority=executor`，返回 external_unavailable。预约追问另被解析成 `relation:预约` 的 bounded 查询，虽读到 m93，仍以 `plan_is_not_completed_event_or_current_fact` 拒绝。

主因是 **意图路由及主体解析错误**，不是模型幻觉、外部服务真的返回未完成，或者证据库没有预约。m93 同时明确保存“还从未做过”、预约时间及 `做过=false`。

“完成清单”单独看可以指外部系统，这是语言歧义；但本题没有命名外部执行器，完整材料能支持截至记录时的个人进展和预约。现有 gold 不修改，不能据关键词自动推断外部权威。若用户确实要求外部最新状态，应明确保留外部状态与已知个人记录的不同证据责任。

## 后续应重设的语义边界

1. **查询理解与权限分开。** chat/live 分类属于可校正的查询理解，不能凭字面词直接剥夺时间候选或整轮判据；owner、角色、scope、撤销、真实日期边界仍由宿主强制执行。
2. **候选包含证据依赖。** 从当前问题及有效用户历史解析实体提及，复用现有索引、结构化别名及来源指纹，补入有界身份依赖。缺身份来源时保持拒绝，不让模型靠关联猜人。
3. **在 claim 层表达事件现状。** 明确否定、未知结果、计划内容和完成报告应独立表达并绑定原文 span；整卡 planned 不应覆盖原文已证明的其他 claim。不能把 `False` 的存在单独当作对应用户问题已被证明，也不能再让一套完整句子正则重做语义审核。
4. **稳定判据协议。** 用可验证引用表达子问题与共同主体，明确复合属性的覆盖；区分 JSON 失败、引用失败、证据不足与候选不足，避免一个问题片段改写丢弃整份判据。具体恢复方式需另行设计和验证，本轮没有实现。

本次分类未发现因合法遗忘、权限或来源撤销必须拒绝的有据题，也未发现最终预算裁剪解释上述缺口。最终生成回答、人格和格式表现须引用相应真实生成评审；这份检索分类不替代回答质量结论。第九现在也是已见数据，任何后续泛化结论仍需新的密封样本。
